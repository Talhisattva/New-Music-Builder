# `0.4.0` vs `0.4.2` Windows Package Investigation

Date: August 3, 2026

## Scope

Compared the packaged Windows release artifacts in `release/` for:

- `NewMusicBuilder-v0.4.0-win64`
- `NewMusicBuilder-v0.4.2-win64`

This comparison covered:

- zip entry counts
- unpacked folder tree/file count
- common-file hash changes
- executable metadata and size
- repo-side packaging/runtime layout changes after `v0.4.0`

## Concrete Findings

### `0.4.0` only

- shipped runtime state inside the packaged folder:
  - `workspace/last_session.json`
  - `workspace/recent.json`
  - `logs/*`
  - `Generated Textures/*`
- shipped packaging leftovers:
  - `numpy-2.4.2.dist-info/*`
  - `customtkinter` `.DS_Store` files

### `0.4.2` only

- no extra packaged-only files were found that did not already exist in `0.4.0`

### Shared package tree differences

- zip entry count is the same for both releases: `1268`
- unpacked package footprint is smaller in `0.4.2`
  - `0.4.0`: `1298` files, `128` directories, `127,371,636` bytes
  - `0.4.2`: `1257` files, `85` directories, `126,461,779` bytes
- the only common files with changed hashes were:
  - `NewMusicBuilder.exe`
  - `_internal/base_library.zip`

### Executable metadata differences

- `0.4.0` exe size: `6,223,844`
- `0.4.2` exe size: `6,231,596`
- `0.4.0` EXE version metadata was blank
- `0.4.2` EXE version metadata is populated:
  - `ProductVersion = 0.4.2`
  - `FileVersion = 0.4.2`

### Repo/code changes after `v0.4.0` that affect runtime/package surface

- runtime state moved from local app folder to `%LOCALAPPDATA%\NewMusicBuilder`
- staging export root moved from workshop-local temp staging to AppData staging on current `main`
- release shaping/pruning logic changed after `v0.4.0`

## Ranked Suspects For Defender Delta

1. `NewMusicBuilder.exe` binary rebuild differences, including the added Windows version resource block
2. `base_library.zip` rebuild differences inside the packaged app
3. post-`0.4.0` packaging/runtime layout changes, even though the `0.4.2` release tree is cleaner overall

## Verdict

Found only weak suspects.

We did **not** find a single concrete packaged file addition in `0.4.2` that cleanly explains the Defender delta by itself.

What we did prove:

- the `0.4.2` package is cleaner than `0.4.0`, not dirtier
- the path-length export failure is unrelated to Defender and is directly caused by the AppData staging path change after `0.4.0`
- the singles regression was a real code contract break and is unrelated to Defender

## Actionable Direction

- keep investigating the binary-level EXE/package build delta
- do **not** block recovery on proving Defender root cause perfectly
- use a `v0.4.0`-based recovery line for the next safe release if Defender remains inconclusive
